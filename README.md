# Menu Photo

메뉴 등록 앱에 올라온 사진과, 현장에서 실제로 제공되는 음식 사진을 나란히 놓고 비교하는 정적 웹 도구입니다.
서버가 없습니다. 브라우저가 GitHub API를 직접 호출해 비공개 저장소에 사진을 넣고 꺼냅니다.

| 파일 | 용도 | 보는 사람 |
|---|---|---|
| `upload.html` | 촬영·업로드 (모바일 우선) | 각 협력사 |
| `index.html` | 비교·리포트·마감 | 관리자 |
| `poc.html` | 설치 전 전제 검증 | 관리자 (1회) |

**이 저장소에는 데이터도 토큰도 들어있지 않습니다.** 화면 코드뿐입니다.
식당 이름·코드·API 주소는 전부 비공개 저장소의 `config.json`에서 실행 시점에 읽습니다.

---

## 1. 구조

```
<전용계정>/menu-photo          공개 · GitHub Pages · 이 저장소 (화면 코드만)
<전용계정>/mp-s1 … mp-s6       비공개 6개 · 식당 한 곳당 하나
    config.json
    photos/YYYY-MM-DD/{slotId}.jpg     ← 당일분만 유지
<전용계정>/mp-ledger           비공개 · 관리자 전용 · 누적 기록 영구 보관
    YYYY-MM.json
```

**왜 저장소를 쪼개나** — "담당 식당만 보이고 다른 식당은 조회조차 안 된다"를 만족시키려면 이 방법뿐입니다.
GitHub의 권한 경계는 저장소 단위이고, 경로 단위 토큰이 없습니다.
A 식당 토큰으로 B 식당 저장소를 호출하면 **404**가 나옵니다 — 저장소가 있다는 사실조차 보이지 않습니다.

## 2. 최초 설치

### 2-1. 전용 계정

개인 GitHub 계정을 쓰지 마세요. 두 가지 이유입니다.

1. 협력사가 자기 토큰으로 `GET /user`를 호출하면 **계정 주인의 로그인·이름·아바타가 보입니다.**
2. 같은 계정의 모든 `<user>.github.io` 프로젝트 페이지가 **오리진을 공유**합니다 —
   같은 계정의 다른 페이지가 localStorage에 있는 협력사 토큰을 읽을 수 있습니다.

담당자가 바뀔 때 인수인계도 전용 계정이 깔끔합니다.

**만드는 법은 평소 계정과 똑같습니다.** `github.com/signup` 에서 새 이메일로 하나 더 만들면 됩니다.
GitHub에 "전용 계정"이라는 별도 종류가 있는 건 아니고, **용도를 분리한다**는 뜻입니다.

다만 약관을 지키려면 이 계정을 **머신 계정(machine account)** 으로 두세요.
GitHub 이용약관은 무료 개인 계정 1개 외에 **자동화 작업 전용 무료 머신 계정 1개**를 따로 허용합니다.
사람이 일상적으로 쓰는 두 번째 개인 계정은 약관상 회색지대지만, 이 계정은
도구가 API로 읽고 쓰는 용도로만 쓰이므로 머신 계정에 해당합니다.
프로필 이름이나 Bio에 자동화용 계정이라고 한 줄 적어두면 분명해집니다.

> **계정 이름에 회사·조직·사업장 이름을 넣지 마세요.** 배포 주소가 `https://<계정>.github.io/...` 라
> 계정 이름이 협력사에게 그대로 보이고 검색에도 걸립니다.

**2단계 인증(2FA)은 반드시 켜세요.** 비밀번호 외에 두 번째 확인을 하나 더 거는 로그인 방식입니다
(인증 앱의 6자리 코드, 패스키, 보안 키 중 택일 — 인증 앱이 가장 무난합니다).

- 선택 사항이 아닙니다. GitHub는 코드를 올리는 계정에 2FA를 의무화했고,
  **2FA를 켜지 않으면 새 토큰(PAT)을 발급할 수 없습니다.** 이 구조는 토큰 7개로 돌아가므로 곧 막힙니다.
- 2FA는 **웹 로그인에만** 걸립니다. 발급된 토큰으로 하는 API 호출에는 영향이 없고,
  협력사는 GitHub 계정이 없으므로 2FA와 무관합니다. 관리자 한 사람의 일입니다.
- **복구 코드(recovery codes)를 반드시 따로 보관하세요.** 인증 앱이 깔린 폰을 잃어버리면
  계정에 못 들어가고, 그러면 사진도 누적 기록도 전부 손이 닿지 않습니다.
  인쇄해서 서랍에 넣든 사내 비밀번호 관리도구에 넣든, **폰이 아닌 곳**에 둬야 합니다.

### 2-2. 저장소 8개

| 저장소 | 공개 설정 | 내용 |
|---|---|---|
| `menu-photo` | **Public** | 이 코드. Settings → Pages → Source: `main` / `/ (root)` |
| `mp-s1` ~ `mp-s6` | **Private** | 식당별. 생성 시 README 추가해서 `main` 브랜치를 만들어 둘 것 |
| `mp-ledger` | **Private** | 누적 기록 |

전부 GitHub Free에서 무료입니다. 비공개 저장소도, 토큰도 추가 비용이 없습니다.

> 저장소 이름에 식당명·사업장명을 넣지 마세요. 협력사 토큰으로 저장소 목록이 보입니다.

### 2-3. `config.json` 작성

식당 저장소 6개 각각의 루트에 넣습니다.

```json
{
  "role":   "store",
  "store":  "<식당 코드>",
  "name":   "<화면에 표시할 식당 이름>",
  "no":     1,
  "origin": "https://<메뉴 API 호스트>",
  "busiCd": "<사업장 코드>",
  "compCd": "<회사 코드>"
}
```

`mp-ledger`의 루트에는 이것만 넣습니다.

```json
{ "role": "ledger" }
```

`role` 값으로 화면이 저장소 종류를 구분합니다. 이 파일이 없는 저장소는 무시됩니다.
`no`는 관리자 화면의 식당 표시 순서(1~6)입니다.

실제 코드 값은 저장소에 적어두지 않았습니다 — `_local/` 폴더의 체크리스트를 보세요.

### 2-4. 토큰 7개 발급

Settings → Developer settings → **Fine-grained personal access tokens** → Generate new token

| 받는 사람 | Repository access | Permissions | 만료 |
|---|---|---|---|
| 협력사 6곳 (각각) | **Only select repositories → 자기 저장소 1개만** | Contents: **Read and write** | 최대치 |
| 관리자 | Only select repositories → 식당 6개 + `mp-ledger` | Contents: **Read and write** | 최대치 |

- `Contents` 외에는 아무것도 켜지 마세요. Metadata(읽기)는 자동으로 붙습니다.
- **만료일을 달력에 적어두세요.** 6곳이 같은 날 한꺼번에 끊깁니다. 만료 30일 전에 재발급합니다.
- 발급 화면을 벗어나면 토큰을 다시 볼 수 없습니다.

### 2-5. 배포

```bash
git init && git branch -M main
git remote add origin https://github.com/<전용계정>/menu-photo.git
git add . && git commit -m "menu photo tool"
git push -u origin main
```

Pages가 올라오는 데 1~2분 걸립니다. 주소는 `https://<전용계정>.github.io/menu-photo/` 입니다.

### 2-6. 전제 검증 — 코드를 쓰기 전에 한 번

`https://<전용계정>.github.io/menu-photo/poc.html` 을 열고 협력사 토큰 하나로 7가지를 실행합니다.
**2번(다른 저장소 404)이 통과하지 않으면 격리가 깨진 것이므로 배포하면 안 됩니다.**
6번(메뉴 API 도달)은 실제 협력사 기기의 네트워크에서 돌려봐야 의미가 있습니다.

### 2-7. 협력사 배포

각 협력사에 **주소와 토큰을 서로 다른 경로로** 전달합니다(예: 주소는 메일, 토큰은 대면·전화).

```
https://<전용계정>.github.io/menu-photo/upload.html
```

첫 화면에서 토큰을 한 번 넣으면 그 기기에 저장됩니다. 식당을 고르는 절차가 없습니다 — **토큰이 식당을 결정합니다.**
휴대폰에서 "홈 화면에 추가"를 하면 앱처럼 열립니다.
공용 태블릿이라면 쓰고 나서 화면 아래 **"이 기기에서 로그아웃"** 을 누르도록 안내하세요.

## 3. 매일 하는 일

**협력사** — 끼니 탭을 고르고, 카드마다 카메라 버튼을 눌러 접시를 찍습니다.
고르는 즉시 긴 변 1280px로 줄여 올라갑니다. 1초 간격 순차 업로드라 25장에 30~60초 걸립니다.

**관리자** — `index.html`에서 날짜를 고르고

1. **02 사진 비교** 에서 앱 사진과 실물 사진을 나란히 확인
2. **03 미업로드** 로 안 올라온 곳 독려
3. **리포트 인쇄 (PDF 저장)** → 인쇄 대화상자에서 대상을 "PDF로 저장"으로. 사진을 모두 받은 뒤 열리므로 몇 초 걸립니다
4. **05 운영 · 마감 → 마감** — 기록을 `mp-ledger`에 남기고 어제 이전 사진을 지웁니다

**순서를 지켜야 합니다. 마감은 사진을 지웁니다 — PDF를 먼저 저장하세요.**
PDF는 과거 메뉴가 API에서 사라진 뒤 남는 **유일한 기록**입니다.

## 4. 분기마다 하는 일 (중요)

### 왜 필요한가

**마감의 "삭제"는 진짜 삭제가 아닙니다.** git은 참조가 끊긴 객체를 한동안 그대로 들고 있고,
커밋 SHA를 적어둔 사람은 지워진 사진을 그대로 받아갈 수 있습니다. GitHub의 정리 작업은 사용자가 돌릴 수 없습니다.

> 그러므로 **"사진은 당일 폐기된다"고 협력사나 사내에 약속하면 안 됩니다.**
> 확실한 폐기는 저장소를 지우고 다시 만드는 것뿐입니다.

용량도 같은 문제입니다. JPEG은 델타 압축이 안 돼서 올린 바이트가 그대로 쌓입니다.
식당당 약 3.5MB/일 ≒ **105MB/월**. 매일 지워도 9~10개월이면 권장 한도 1GB에 닿습니다.
관리자 화면 **05 운영** 에 저장소별 용량이 나오고 500MB에서 경고가 뜹니다.

### 절차

1. 그 분기의 PDF 리포트가 전부 보관돼 있는지 확인
2. 식당 저장소 6개를 **삭제하고 같은 이름으로 다시 생성**
3. `config.json` 6개 다시 넣기
4. **토큰 6개 재발급** — 토큰은 저장소에 묶여 있어서 재생성하면 전부 무효가 됩니다
5. 협력사 6곳에 새 토큰 배포. 각 기기에서 로그아웃 후 새 토큰 입력

`mp-ledger`는 건드리지 않습니다. 누적 지표는 여기 남습니다.

**히스토리 축소** 버튼(05 운영)은 커밋 이력만 1개로 줄입니다. 용량이 바로 줄지 않을 수 있고,
위의 "진짜 삭제가 아니다" 문제를 해결하지 못합니다. 재생성을 대신하지 않습니다.

## 5. 알고 시작할 것

- **GitHub 이용약관** — GitHub는 저장소를 파일 스토리지·CDN으로 쓰는 것을 권장하지 않는다고 명시합니다.
  하루 약 21MB, 연 약 7.7GB를 API로 계속 쓰는 패턴입니다. 현재 규모에서 당장 문제될 가능성은 낮지만,
  대상을 늘릴 때 가장 먼저 걸릴 항목입니다.
- **토큰 유출** — 유출되면 해당 식당 저장소 하나만 영향을 받습니다. 다만 메신저·스크린샷·공용 기기를 통한
  유출은 GitHub가 자동으로 막아주지 않습니다(공개 저장소에 커밋된 토큰만 자동 폐기). **수동 폐기·재발급이 1차 통제 수단입니다.**
- **기록의 신뢰 범위** — 협력사 토큰은 자기 저장소를 전부 덮어쓸 수 있고 커밋 작성자도 임의로 적을 수 있습니다.
  그래서 누적 기록은 협력사가 쓰지 않고, **마감 때 관리자가** 저장소를 읽어 기록합니다.
  믿을 수 있는 신호는 "어느 저장소에 들어왔는가"까지입니다. 개인 단위 책임 추적은 이 구조로 보장되지 않습니다.
- **메뉴 API** — 남의 공개 엔드포인트입니다. 화면을 열 때만 호출하고 자동 폴링은 넣지 않았습니다. 그대로 두세요.
- **서비스 워커** — 같은 출처의 화면 코드만 캐시합니다. GitHub API 응답은 **절대 캐시하지 않습니다**
  (공용 기기 캐시에 남의 사진이 남지 않도록). `sw.js`를 고칠 때 이 규칙을 깨지 마세요.

## 6. 더 나은 선택지 (참고)

외부 서비스 사용이 허용된다면 Cloudflare Worker 같은 **토큰 중계기**가 더 깔끔합니다 —
기기에 토큰을 두지 않고, 협력사별 비밀번호를 쓰고, 진짜 감사 로그가 남고, 저장은 R2로 분리됩니다.
현재 구성은 "사내 GitHub가 업로드를 못 받는다"는 제약에서 출발한 것이라, 제약이 풀리면 다시 볼 만합니다.

## 7. 손볼 때

빌드 도구가 없습니다. 파일을 고치고 `git push` 하면 끝입니다(Pages 반영까지 1~2분).

| 파일 | 역할 |
|---|---|
| `js/github-api.js` | GitHub 호출 **단일 창구**. 쓰기 직렬 큐·백오프·일괄 커밋이 전부 여기 |
| `js/menu-api.js` | 메뉴 조회. 식별정보를 넣지 않는다 — `config.json`에서 받는다 |
| `js/chart-kit.js` | 디자인 시스템 원본 사본. **고치지 않는다** |
| `assets/theme.css` | 디자인 시스템 원본 사본. **고치지 않는다** |
| `assets/photo.css` | 이 도구 전용 컴포넌트 + 인쇄 레이아웃 |

주의할 두 가지가 `js/github-api.js` 주석에 적혀 있습니다.

1. **쓰기는 반드시 직렬.** `PUT /contents`는 매번 브랜치를 전진시켜서, 같은 저장소에 동시 PUT 하면
   두 번째가 409를 받습니다. 재시도 튜닝으로 해결되는 문제가 아닙니다.
2. **일괄 삭제에 `DELETE`를 쓰지 않는다.** 삭제도 커밋이라 시간당 한도(500건, 계정 공유)를 먹습니다.
   Git Data API로 커밋 1개에 처리합니다 — 141콜이 4콜이 됩니다.

`fetch`에 `credentials:'include'`나 커스텀 헤더를 추가하지 마세요. CORS 프리플라이트가 깨집니다.
